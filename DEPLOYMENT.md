# Deploying to Render

Both `apps/api` and `apps/web` deploy as separate Render web services from
this one repo, using the `render.yaml` Blueprint at the repo root. The
database (Neon) and image storage (Cloudinary) are external managed
services you set up separately - Render just needs their connection details
as environment variables.

## One-time setup

1. **Neon**: create a Postgres project if you haven't already, and copy its
   connection string (`DATABASE_URL`).
2. **Cloudinary**: grab your cloud name, API key, and API secret from the
   dashboard.
3. **Push this repo to GitHub/GitLab** (Render deploys from a git remote).
4. In Render, choose **New > Blueprint** and point it at this repo. It will
   read `render.yaml` and create two services: `isociety-api` and
   `isociety-web`.

## Environment variables

Render creates the env var *names* from `render.yaml` automatically, but
anything marked `sync: false` needs its actual value filled in by hand in
the Render dashboard (Service > Environment) - these are secrets/URLs it
can't know in advance:

**`isociety-api`**
| Variable | Value |
|---|---|
| `DATABASE_URL` | Your Neon connection string |
| `CORS_ORIGIN` | The web service's URL (see chicken-and-egg note below) |
| `APP_BASE_URL` | Same as `CORS_ORIGIN` - it's used to build registration links and QR codes |
| `CLOUDINARY_CLOUD_NAME` / `CLOUDINARY_API_KEY` / `CLOUDINARY_API_SECRET` | From Cloudinary |

`JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` are auto-generated by Render on
first deploy (`generateValue: true`) - you don't need to set those yourself.

**`isociety-web`**
| Variable | Value |
|---|---|
| `NEXT_PUBLIC_API_URL` | The API service's URL with `/api` appended, e.g. `https://isociety-api.onrender.com/api` |

### Chicken-and-egg URLs

`CORS_ORIGIN`/`APP_BASE_URL` (on the API) and `NEXT_PUBLIC_API_URL` (on the
web app) each need to know the *other* service's URL, which Render only
assigns once a service is first created. The simplest path:

1. Deploy both services once with placeholder values (or leave them blank -
   the app will still boot, registration links and CORS will just be wrong
   until step 2).
2. Once Render shows you both `*.onrender.com` URLs, fill in the real values
   and redeploy (Environment tab > Save Changes triggers a redeploy).
3. Once you have your actual domain, point it at `isociety-web` and update
   `CORS_ORIGIN`/`APP_BASE_URL`/`NEXT_PUBLIC_API_URL` again. `CORS_ORIGIN`
   accepts a comma-separated list, so you can keep the `.onrender.com` URL
   working alongside the custom domain during the switch.

## What happens on every deploy

- The API's build step runs `prisma generate`, then `prisma migrate deploy`
  (applies any pending migrations against `DATABASE_URL`), then type-checks
  via `tsc`. It actually **runs** via `tsx src/index.ts`, not the compiled
  output - `@isociety/shared` and `@isociety/database` are consumed as raw
  TypeScript source with no build step of their own (same as local `pnpm
  dev`), and tsx transpiles whatever it imports on the fly. The `tsc` build
  step still exists purely as a type-check gate that fails the deploy on a
  type error.
- The web service runs a normal `next build` / `next start`.
- Render's health check hits `GET /api/health` on the API service; if it
  doesn't return 200 within the configured timeout, the deploy is rolled
  back automatically.

## Local production build check

Before pushing, you can sanity-check the exact commands Render will run:

```bash
pnpm install --frozen-lockfile
pnpm --filter @isociety/database run generate
pnpm --filter api run build
pnpm --filter web run build
```
